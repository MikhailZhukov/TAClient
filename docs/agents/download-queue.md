# Download Queue

Stable-scroll polling contract — the list must not "jump to the top" during active downloads.

- **No page-1 collapse:** the 3s polling loop's reconcile (`DownloadQueueViewModel.performPollTick`, the testable seam extracted from `startPolling`) NEVER calls `loadDownloads(page: 1)`. It reconciles via `reconcileLoadedPages()` → `fetchAllLoadedPages(filter:upTo:)`, which preserves pagination depth and `currentPage` (only clamped down via `min(currentPage, newLastPage)`, never reset to 1). The old page-1 collapse was the root cause of scroll being thrown to the top during active downloads.
- **Depth-preserving mutation reload (`reloadPreservingDepth`):** `loadDownloads(isRefresh:)` is the page-1 RESET primitive (`getDownloads(page: 1)`, `currentPage = 1`) — correct ONLY for `refresh()` (pull-to-refresh) and `onFilterChanged()` (tab switch). Every OTHER post-mutation reload — `addToQueue` (the add bar is always visible for privileged users, so reachable mid-download), `stopCurrentDownload`, and the `updateStatus` / `deleteItem` error-recovery branches — MUST use `reloadPreservingDepth()` instead, or it throws scroll to the top during active downloads (the residual half of the original bug that `859eb97` only fixed for the polling loop). `reloadPreservingDepth` refetches pages `1...currentPage` for the **current** `filter` (filter-aware, unlike `reconcileLoadedPages` which is pending-only), reconciles via `applyPolledItems`, applies the same post-await TOCTOU/depth guard as `reconcileLoadedPages`, and is **silent** (does NOT toggle `isLoading` — no full-screen spinner flash). It surfaces failures via `router.handleError` (mutations are user-initiated and should report), unlike `reconcileLoadedPages` which throws to be swallowed by `performPollTick`'s `catch { return true }`. Do NOT unify the two error strategies.
- **TA `last_page: 0` on the final page (collapse-to-top root cause):** the TA download API returns `paginate.last_page == 0` when the requested page IS the last page (pages 1..N-1 correctly report N). Trusting that `0` verbatim was the ACTUAL root cause of "the deep-scrolled queue jumps to the top when you queue a download" (confirmed in production `[DLQ]` logs: `loadMore page 15 … lastPage=0` → reconcile `currentPage = min(15, 0) = 0` → next `fetchAllLoadedPages(upTo: 0)` refetches page 1 only → `items 178 -> 12`). Fixed at TWO layers: (1) **`DownloadRepositoryImpl.getDownloads`** resolves a non-positive `last_page` to the actually-loaded page (`resolvedLast = reportedLast > 0 ? reportedLast : resolvedPage`) so `lastPage` is never reported below the page just fetched — the primary fix; (2) **`DownloadQueueViewModel.clampDepth(newLastPage:currentPage:)`** is a defense-in-depth backstop used by BOTH `reconcileLoadedPages` and `reloadPreservingDepth` in place of the raw `currentPage = min(currentPage, newLastPage)` — a non-positive `newLastPage` keeps the current depth (no clamp), a genuinely-smaller positive `newLastPage` still clamps (real queue shrink) but never below 1, and `fetchAllLoadedPages` additionally floors `pages` at `max(1, pages)`. The genuine-shrink path (`last_page` drops to a smaller POSITIVE value as videos leave the pending queue) is unchanged and still clamps depth down. Tests: `DownloadRepositoryImplTests.getDownloads_lastPageZeroOnFinalPage_resolvesToRequestedPage` (repo) + `DownloadQueueViewModelTests.performPollTick_lastPageZeroOnFinalPage_doesNotCollapseDepth` (VM guard, two ticks) alongside the existing `performPollTick_lastPageShrinks_clampsCurrentPage…` which pins the genuine-shrink behaviour.
- **`fetchAllLoadedPages(filter:upTo:)` is parameterized:** it no longer hardcodes `"pending"` / `currentPage`. `reconcileLoadedPages` passes `filter: "pending"` literally (its pending-only no-op on the ignore tab comes from its OWN top `guard filter == "pending"`, NOT from the fetch hardcoding); `reloadPreservingDepth` passes the live `filter`. The polling contract is unchanged.
- **Grace + fast-stop polling-stop contract:** `performPollTick` does NOT stop on the first idle tick. An idle tick (no `download`-prefixed notification group) also occurs during `download_pending` startup latency and in the quiet gap between two videos (indexing/thumbnail work emits no `download` group) — stopping then killed polling mid-batch (banner vanished, list stopped reconciling). New logic: an **active** tick resets `consecutiveIdlePolls` and returns `true`; an **idle** tick reconciles first, then (a) **fast-stops** (`return false`) immediately if `filter == "pending"` and `items.isEmpty` (queue drained = definitely done), else (b) increments `consecutiveIdlePolls` and returns `false` only once it reaches `maxIdlePollsBeforeStop` (= 4 → ~12s of confirmed inactivity), otherwise `true`. Within the grace window the banner is NOT blanked to empty (preserved unless `notifications` is non-empty) so it doesn't flicker between videos. The higher bound is cheap because fast-stop handles true completion instantly; grace only governs the rarer "downloads stopped but queue not drained" case. `consecutiveIdlePolls` resets in `startPolling()` and on every active tick.
- **Identity-preserving updates:** `applyPolledItems` is `@discardableResult -> Bool` with an equality short-circuit (returns `false` / no reassignment when the filtered result equals current `items`, so SwiftUI sees no change). List updates rely on SwiftUI `List` diffing by `DownloadItem.id` (== `youtubeId`) for identity-preserving reorders/removals, animated via `.animation(.default, value: viewModel.items)` in the View.
- **Swipe-triggered mutations MUST be surgical, never a full-array reload:** the row swipe actions run their `Task` while the swipe's commit animation is still in flight. `deleteItem` (trailing), `updateStatus(ignore/pending)` (trailing), and `downloadItem` (**leading** green "download") therefore mutate `items` ONLY via an in-place `items.removeAll { $0.youtubeId == id }` (single-row delete SwiftUI List animates in place). Do NOT call `reloadPreservingDepth()` (or any whole-array reassignment) from a swipe-action path: replacing `items` mid-swipe makes UICollectionView drop the triggered swipe's mask view (`unexpected removal of the current swipe occurrence's mask view`) and reset `contentOffset` to the top — the list jumps. `downloadItem`'s removal is **filter-gated**: `priority` pulls the video out of the ignore list, so on the **ignore** tab remove the row (mirrors the trailing swipes); on the **pending** tab the item stays pending in place — mutate nothing, and let the next poll tick surface its reordered position. `addToQueue`/`stopCurrentDownload` keep `reloadPreservingDepth()` because they are NOT swipe-triggered (add bar / toolbar). Regression history: `ac67984` first fixed the ignore-tab "moved row lingers" bug with a `reloadPreservingDepth()` in `downloadItem`, which reintroduced the scroll-jump for the leading swipe; the surgical removal fixes both without a jump.
- **Progress banner is a top safe-area inset, NOT a List sibling:** the `downloadProgress` banner and the inline error bar are rendered via `.safeAreaInset(edge: .top)` on `DownloadQueueView`, not as siblings inside the VStack above the `List`. A safeAreaInset adjusts the scroll view's content inset, which PRESERVES `contentOffset`; a sibling that inserts/resizes/removes above the List (as they were originally, inside a `.geometryGroup()`) re-lays the subtree and resets the List scroll to the top — the banner toggles every batch start/finish and its height changes each poll tick during active downloads, so this reset fired repeatedly while downloads ran (root cause of the "scroll jumps to top during active downloads" bug that survived the pagination-depth fixes). The `.geometryGroup()` (a leftover from the initial release, only ever needed for the adaptive LazyVGrid in the video list — this is a plain `List`) was removed at the same time. The inset VStack carries a `.background(.bar)` so scrolled content doesn't show through, and is zero-height/invisible when both the banner and inline error are absent. Do NOT move the banner back above the List.
- **Constant-height progress header:** `TaskNotificationBanner` reserves a fixed height tick-to-tick — the message line always renders (non-breaking-space placeholder when empty, `lineLimit(1)`) and the progress bar is always rendered with `.opacity(info.isError ? 0 : 1)` (hidden on error but layout space kept). The whole `downloadProgress` block is fully absent when `downloadProgress.isEmpty` (no reserved empty space at idle), animated in/out.
- **Test seam:** `performPollTick` and `applyPolledItems` are `internal` (not `private`) for `@testable import` access. `maxIdlePollsBeforeStop` is an `internal static let` so grace-window tests loop off the constant instead of hardcoding tick counts. Covered by `DownloadQueueViewModelTests` (incl. `reloadPreservingDepth` depth-preservation on `addToQueue`/`stopCurrentDownload`/error paths, filter-awareness on the ignore tab, grace/fast-stop/banner-continuity for `performPollTick`, and the swipe-safe surgical removal for `downloadItem` — `downloadItem_onIgnoreTab_removesMovedRow_surgically_withoutRefetch` asserts the row leaves with NO extra `getDownloads` call, `downloadItem_onPendingTab_keepsItemInPlace_noRemoval` asserts the pending row is untouched).
